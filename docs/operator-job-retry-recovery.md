# Проверка и восстановление повторной обработки заказов

Новый код ограничивает обработку заказа пятью попытками по умолчанию (`JOB_PROCESSING_MAX_ATTEMPTS`). Счётчик существующих заказов не сбрасывается при обновлении: перед применением новой версии сначала проверьте список старых заказов с числом попыток на уровне лимита. Команду необходимо запускать только с явно заданным `DATABASE_URL`; пароль не следует помещать в историю команд или отчёты.

Из корня проекта read-only отчёт:

```bash
PYTHONPATH=. .venv/bin/python scripts/ops_job_retry_recovery.py
```

Отчёт включает как уже исчерпанные повторы, так и ещё не обработанные старые записи, которые достигнут лимита при следующем захвате. Вывод ограничен 100 записями; для конкретного заказа используйте `--id UUID`. Отчёт не является полной выгрузкой при большом числе записей.

После проверки конкретного исчерпанного заказа можно явно вернуть его в очередь:

```bash
PYTHONPATH=. .venv/bin/python scripts/ops_job_retry_recovery.py --id UUID --apply
```

Разрешены только `permanent_error` с причиной `retry_exhausted`, без текущего claim, любых откликов и попыток отправки. Операция сбрасывает счётчик и сохраняет время и прежнее число попыток в данных заказа; идентичность оператора не фиксируется. Сама команда не отправляет отклик, но работающий worker может начать генерацию и поставить уведомление в Telegram, поэтому учитывать это до применения. Рабочая БД этими проверками не менялась.

Старые и новые workers нельзя смешивать: прежние процессы могут не соблюдать новый предел и продление захвата. До rollout необходимы отдельно согласованные инвентаризация, проверка схемы и согласованный перезапуск всех соответствующих процессов.
