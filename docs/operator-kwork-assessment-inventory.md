# Проверка оценок Kwork

Команда составляет ограниченный отчёт по последним заказам Kwork. Она не обращается к Kwork, LLM или Telegram, не обновляет данные и выполняет запросы в транзакции PostgreSQL `READ ONLY`. В отчёте только ID заказа, сохранённый статус и результат проверки оценки; текст заданий и данные заказчиков не выводятся.

Для безопасной проверки сначала явно укажите URL отдельной тестовой базы через переменную `DATABASE_URL`, затем выполните:

```bash
.venv/bin/python scripts/inspect_kwork_assessments.py --limit 100
```

`--limit` принимает от 1 до 1000, по умолчанию 100. Проверяются только самые новые записи в пределах лимита; это не отчёт обо всех заказах. Без явно заданной переменной окружения команда не выбирает рабочую базу автоматически. Не передавайте пароль аргументом командной строки и не публикуйте URL базы.

Значения `buyer_not_eligible`, `assessment_required`, `assessment_stale` и `assessment_ineligible` означают блокировку по соответствующему правилу. При `pass` выполнена только проверка оценки на сохранённых данных: это не подтверждение актуальности Kwork, готовности к отправке, проверки других защит или одобрения человеком.

Изменение данных заказчика и полей заказа отзывает прежнюю оценку. После привязки оценки к конкретному buyer ID ранее созданные оценки также потребуется получать заново. Автоматического безопасного процесса повторной оценки и выпуска новой карточки ещё нет; команда его не запускает. Не обходите блокировки прямым редактированием базы: нужны свежее получение источника, новая оценка и отдельное человеческое review. Действия с рабочей базой и развёртывание подлежат отдельному согласованию.

## Подготовленная переоценка одного заказа

Код содержит отдельную команду для ручной переоценки. Её запуск изменяет сохранённую оценку и вызывает настроенный LLM-провайдер; это может расходовать квоту или деньги. Она не получает данные с Kwork и не отправляет предложения или сообщения. Запускать на рабочей базе только после отдельного согласования и проверки настроек провайдера.

Перед запуском карточка должна быть заново получена scraper и сохранена не более 15 минут назад, с подтверждёнными показателями покупателя и полным описанием. Старая дата создания/истекший срок, уже отправленный заказ, активная обработка или неопределённая отправка блокируют операцию. Если текущий scrape не нашёл карточку, команда не считает старую запись свежей.

После явной установки `DATABASE_URL` и проверки подключённого LLM операционная команда выглядит так:

```bash
.venv/bin/python scripts/reassess_kwork_job.py JOB_UUID --apply --confirm-llm
```

`accepted` означает только положительную оценку; `rejected` — отрицательную, `blocked` — отсутствие изменения с кодом причины. Все ранее представленные карточки и старые одобрения перестают соответствовать новой оценке, даже когда цена совпадает. Чтобы показать существующий подходящий отклик заново, используйте `/rereview` по [отдельной инструкции](operator-review-reissue.md); это ставит новую карточку в очередь, но само по себе не подтверждает и не отправляет отклик. Заказ, результат которого изменился во время оценки, не обновляется. Автоматического поиска и обновления конкретной старой карточки ещё нет.

Проверка операции выполнена на изолированной БД и синтетической HTML-карточке, через реальный FilterAgent с подставным ИИ до постановки нового review в очередь; работающий сервис, реальный Kwork и связка с настоящим LLM после этих изменений не проверены.
