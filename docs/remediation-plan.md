# План исправлений JobPilot AI

Дата: 13 октября 2026. Основание: [аудит](audit-2026-10-13.md).
Документы для исполнения: [чеклисты](remediation-checklists.md), [промпт](remediation-prompt.md).

## Цель

Сделать полный цикл «заказ → оценка → черновик → одобрение → отправка → переписка → результат» управляемым, восстанавливаемым после сбоя и защищённым от несанкционированных действий. Сохранить human approval, текущую маршрутизацию моделей, стратегию первых отзывов и накопленные данные.

Аудит — список гипотез и подтверждённых дефектов текущего кода, а не замена воспроизведению. Перед исправлением перепроверять каждый пункт. В частности, полная пауза Kwork может быть намеренным поведением: сохранить её как отдельный режим, а поведение паузы по коннектам задавать явно.

## Правила исполнения

- Не затирать существующие незакоммиченные изменения. Зафиксировать исходное состояние рабочего дерева и результаты проверок.
- Одна законченная группа поведения — один небольшой набор изменений. Отдельные коммиты/PR только в рамках разрешённого пользователем Git-процесса.
- Каждый этап заканчивается проверкой его критериев из чеклистов. CI и тесты добавлять вместе с исправлениями, а не откладывать до конца.
- Все локальные и интеграционные проверки используют fake платформу/LLM и отдельную тестовую БД. По умолчанию без сообщений клиентам, платных запросов и расходов коннектов.
- Сначала подготовить и проверить миграции на копии данных. Работа с действующей БД, внешние отправки и deployment — отдельный явно разрешённый шаг.
- Не обещать exactly-once для внешнего API без его idempotency key. Локально обеспечивать один claim; после неопределённого внешнего результата выполнять сверку или ручное разрешение.
- Не держать транзакцию или row lock во время LLM, браузера или сетевой отправки.

## Этап 0. Воспроизводимая исходная точка

**Пункты аудита:** 21, 23. **Зависимости:** нет.

1. Прочитать локальные инструкции, актуальный код, diff и аудит. Подтвердить дефекты; записать расхождения.
2. Сохранить результаты pytest, Ruff, pip check и список активных сервисов. Исходный результат аудита: 62 passed / 3 failed, 29 замечаний Ruff.
3. Убрать зависимость тестов паузы от текущей даты: внедрить контролируемый clock или фиксировать время в тестах. Проверить до/в день/после возобновления и смену года.
4. Удалить повторные определения ensure_proposal_greeting, сверив всех вызывающих и действующую сигнатуру; исправить замечания Ruff без массового форматирования постороннего кода.
5. Подключить базовый CI: lint и unit tests без настоящих секретов. Подготовить отдельную конфигурацию integration tests.

**Результат:** чистый baseline либо документированные независимые блокеры; запуск проверок воспроизводится из README.

## Этап 1. Контроль доступа

**Пункты аудита:** 1, 2. **Зависимости:** этап 0.

1. Ввести обязательную проверку API token для данных и управляющих маршрутов. Не хранить и не логировать токен. Ограничить длины входов, диапазон limit и частоту дорогих запросов.
2. Оставить публичную liveness-проверку без чувствительных данных; определить доступ к readiness и подробной диагностике.
3. Общая авторизация всех Telegram routers: разрешённый user_id и chat_id, включая /dev, FSM-сообщения и callbacks.
4. Для callback проверить принадлежность pending к chat/message, действующий статус и версию текста. Для устаревшей карточки не выполнять действие.
5. Закрыть публикацию внутренних портов или привязать к localhost. Убрать фиксированный пароль БД; обеспечить совместимую настройку локальной разработки.
6. Проверить сетевую публикацию Cursor bridge proxy: токен обязателен, bind ограничен нужным контейнерным доступом. Не менять bridge протокол без проверки его реализации.

**Результат:** посторонний пользователь не читает данные, не запускает задачи и не выполняет отправку; легитимный admin workflow сохранён.

## Этап 2. Единая схема БД и модель состояний

**Пункты аудита:** 6, 7, 19. **Зависимости:** этап 1.

1. Сделать Alembic источником изменения схемы. Для чистой БД — upgrade до head; для существующей — документированный baseline после проверки совместимости, без слепого stamp.
2. Подготовить read-only preflight: дубли job identity, дубли client identity, несколько активных proposals, некорректные scores и orphan references. Не удалять дубли автоматически.
3. Добавить UNIQUE(platform, external_id) для заказов, CHECK score 0..100, индексы очередей и подходящую уникальность клиентов с известной идентичностью.
4. NULL external_id не использовать для поиска общего клиента. Не объединять записи по имени без доказательства идентичности.
5. Определить допустимые состояния job, proposal, approval, notification и send attempt. Генерация, одобрение и внешняя доставка должны иметь отдельные состояния.
6. Добавить claim owner/token, время lease, счётчик попыток и next_attempt_at там, где это нужно. Уникальность активного draft определить с учётом edited/approved/sending и допустимых версий.
7. Заменить параллельный create_all + SQL bootstrap миграциями. Запускать migration один раз перед сервисами, а не одновременно из каждого entrypoint.

**Результат:** повтор сохранения заказа идемпотентен; схема чистой и обновлённой БД совпадает; терминальные состояния не перезаписываются новым pipeline.

## Этап 3. Надёжный inbox и доставка Telegram

**Пункты аудита:** 3, 10. **Зависимости:** этап 2.

1. Сохранять входящие сообщения в БД по уникальному platform/thread/message key. Разделить «получено», «обработано» и «уведомлено».
2. В одной транзакции сохранять входящее/черновик и событие outbox. Ошибка генерации не должна уничтожать исходное сообщение.
3. Обрабатывать outbox отдельной задачей: атомарный claim, ограниченный backoff с jitter, восстановление lease, dead-letter/needs_attention после исчерпания попыток.
4. Для откликов создавать outbox вместе с proposal, чтобы pending без message_id автоматически восстанавливался.
5. Файловый seen-state перестать использовать как единственный источник истины. Документировать импорт/первый запуск и поведение старых непрочитанных сообщений.
6. После timeout Telegram учитывать возможность уже доставленной карточки. Устаревшие и повторные карточки обязаны ссылаться на одно действие и не разрешать повторную внешнюю отправку. Не обещать отсутствие дублей Telegram при неизвестном результате sendMessage.

**Результат:** сообщение и запрос одобрения сохраняются при сбоях БД/LLM/Telegram и после рестарта; ошибки видны и допускают управляемое восстановление.

## Этап 4. Атомарная отправка откликов и ответов

**Пункты аудита:** 4, 5, 7. **Зависимости:** этапы 2–3.

1. Общий механизм send attempts для proposal и reply; все пути, включая скрипты и Telegram, используют его.
2. Одобрение фиксирует конкретную неизменяемую версию текста, цену и параметры отправки. Редактирование после одобрения создаёт новую версию и требует нового одобрения.
3. В короткой транзакции выполнять compare-and-set claim по бизнес-объекту. Сохранить attempt до сетевого вызова и завершить транзакцию.
4. После внешнего вызова фиксировать confirmed_sent, known_failed либо unknown_result. Статус sent означает подтверждение площадки.
5. При unknown_result выполнить безопасную read-only сверку. Если однозначная сверка невозможна, блокировать автоматический повтор и показывать needs_attention.
6. Истечение lease не означает, что отправка не произошла. Старый worker не должен завершить чужой новый claim; проверять fencing token и учитывать сверку внешнего результата.
7. Разделить новый отклик и обновление существующего. Проверять связь proposal.job_id с job_id, актуальность заказа, допустимость resubmit и одобренный content hash.

**Результат:** повторный клик, параллельные процессы и рестарт не создают новую отправку без проверки; неопределённость не маскируется успехом или обычной ошибкой.

## Этап 5. Устойчивый pipeline и строгие ответы LLM

**Пункты аудита:** 8, 11, 12, 18. **Зависимости:** этапы 2–4.

1. Атомарно захватывать job на обработку; повтор beat не дублирует обработку активной записи. Восстанавливать зависшие claims.
2. Разделить filtered/scored и retryable/permanent processing errors. Сохранять этап, тип ошибки и next_attempt_at; не превращать сбой LLM в бизнес-отказ.
3. Валидировать ответы filter/scoring/chat/learning через Pydantic. Для scoring нужны все критерии, конечные числа 0..100; некорректный JSON не получает проходной балл.
4. Ограничить timeout, retries, конкуренцию и затраты задач. Не пересчитывать неизменившийся pending/approved/sent заказ автоматически.
5. Перейти на асинхронный Qdrant доступ, ленивую инициализацию и генерацию без retrieval при недоступной памяти. Индексацию вынести в повторяемую задачу.
6. Разделить глобальную ручную паузу и автоматическое ограничение отправки из-за коннектов. Зафиксировать совместимость с текущей намеренной полной паузой; не возобновлять её без явного изменения настройки.
7. Изолировать ошибки между площадками и отдельными заказами, сохраняя диагностический результат вместо тихого пустого успеха.

**Результат:** временный сбой не теряет заказ; повреждённый ответ LLM не одобряет его; политика паузы прозрачна и проверена.

## Этап 6. Корректная переписка и сбор заказов

**Пункты аудита:** 9, 14, 19, 20. **Зависимости:** этапы 2–5.

1. Нормализовать platform project_id и thread_id, заменить LIKE/ILIKE по подстроке точной идентичностью.
2. При нескольких подходящих заказах использовать состояние needs_context и выбор в Telegram. Не генерировать уверенный ответ с произвольно выбранным заказом.
3. Общий context service для /chat и inbox: конкретный thread, фактически отправленный proposal snapshot, история, summary и последнее сообщение.
4. Draft ответа хранить отдельно от фактически отправленного outbound interaction. Генерация не должна записываться как реальная отправка.
5. Ключ summary cache строить по thread и версии/хешу содержимого, а не только числу сообщений; учитывать изменения и усечение истории.
6. Generic scraper: urljoin, канонический URL/ID площадки, безопасное чтение optional fields. HTML-фикстуры на карточки без полей и одинаковые заголовки.
7. Upwork/FL.ru явно обозначить экспериментальными и не включать в обещанный полный цикл, пока нет подтверждённого extraction/login/sender.

**Результат:** ответ относится к правильному заказу и реальной истории; повтор scrape не меняет идентичность заказа из-за заголовка.

## Этап 7. Исходы, обучение и семантическая память

**Пункты аудита:** 13, 15, 16, 17. **Зависимости:** этапы 4–6.

1. Enum исходов и допустимые переходы. Уникальный event/idempotency key; отдельно определить однократную награду за этап результата и правила исправления ошибочного исхода.
2. Сначала транзакционно записывать outcome/reward, потом создавать событие обучения. Повтор API не увеличивает reward и не запускает новую обучающую запись.
3. Передавать learning фактически отправленный proposal ID/version/text. Индексация успешного примера идемпотентна и восстанавливается после сбоя Qdrant.
4. Веса: точный набор критериев, finite/nonnegative values, ненулевая сумма, нормализация, одна активная версия. Порог данных и измеримая оценка перед активацией.
5. Review-first стратегию сохранить; ясно показывать, когда обученные веса применяются, а когда используется фиксированная политика.
6. Независимый embedding provider; metadata модели/размерности/версии и отдельные коллекции. Отключить hash fallback для semantic search. Переиндексацию выполнять без потери старой коллекции.

**Результат:** hired учитывается один раз, успешный текст доступен памяти, а смена LLM не смешивает пространства embeddings.

## Этап 8. Эксплуатация и выпуск

**Пункты аудита:** 21–23. **Зависимости:** этапы 0–7.

1. Lockfile и установка с проверкой его неизменности; CI: lint, unit, integration на PostgreSQL/Redis, миграции чистой/старой БД и сборка образа.
2. Отдельный production compose: без reload, non-root, restart policies, корректные readiness/healthcheck, ограниченные порты и конфигурируемые host-пути.
3. Метрики: последний успешный scrape/inbox, возраст очереди/outbox, ошибки, unknown_result, количество внешних отправок, расход LLM/коннектов. Без секретов и полного текста переписки в обычных логах.
4. Runbook: обновление, миграции, остановка beat/отправок, recovery claims, ручное разрешение unknown_result, откат приложения.
5. Backup и восстановление PostgreSQL, Qdrant и нужных файлов состояния/сессий; проверить восстановление в изолированной среде. Откат версии приложения не считать откатом данных или внешних сообщений.
6. Обновить README/.env.example: порты, режимы пауз, список поддерживаемых площадок, auth, migration и команды проверки.
7. Выпуск: тестовая среда → dry-run без внешних отправок → отдельно разрешённая контролируемая реальная проверка → ограниченная автоматизация с наблюдением.

**Результат:** установка и восстановление воспроизводимы; оператор видит остановку потока и умеет безопасно восстановить работу.

## Этап 9. Улучшения продукта после закрытия дефектов

1. Telegram-очередь errors/unknown_result/needs_context с объяснимыми действиями восстановления.
2. Актуальность и закрытие заказа до дорогой генерации; reason codes фильтрации и ручной override с журналом.
3. Воронка по уникальным заказам, конверсия и стоимость результата; разделение черновиков, одобрений и подтверждённых отправок.
4. История отправленных версий текста/цены/сроков и статус подтверждения платформы.
5. План полноценной поддержки новых площадок — только после устойчивого Kwork-сценария.

Этот этап не должен откладывать исправление P1. Оценки сроков назначаются после preflight и проверки реальной схемы БД; сроки из одного статического аудита были бы недостоверны.
