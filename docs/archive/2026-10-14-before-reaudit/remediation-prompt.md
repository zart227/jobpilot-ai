# Готовый промпт для реализации

Скопируй следующий блок в чат агента, работающего в этом репозитории.

```text
Работай в /home/arthur/Projects/personal/jobpilot-ai. Реализуй исправления JobPilot AI по документам:
- docs/audit-2026-10-13.md
- docs/remediation-plan.md
- docs/remediation-checklists.md

Твоя задача — последовательно исправить подтверждённые проблемы, начиная с P1, затем P2 и эксплуатационных P3. Нужны изменения кода, миграции, необходимые тесты, документация и фактические доказательства проверок. Не ограничивайся повторным аудитом или предложением плана.

Сначала прочитай применимые AGENTS.md/инструкции, документы, актуальный код и git diff. В рабочем дереве уже есть незакоммиченные изменения: сохрани их, не делай reset/checkout поверх них и не переписывай чужие изменения. Не создавай commits/PR, не публикуй и не развёртывай изменения без отдельного указания. Если файлы изменились после аудита, проверяй реальные дефекты заново и записывай расхождения.

Следуй порядку этапов из плана, учитывая зависимости. Сразу стабилизируй тесты, зависящие от даты, и baseline lint. Для каждой группы изменений: воспроизведи дефект, внеси минимальное достаточное исправление, выполни значимые проверки, обнови чеклист с доказательствами и переходи дальше. Непроверенные пункты не отмечай выполненными. Если отдельная внешняя проверка недоступна, продолжай независимые локальные задачи и явно фиксируй ограничение.

Сохрани поведение human approval: ни новый отклик, ни отредактированный текст, ни ответ клиенту не отправляется без одобрения конкретной версии. Сохрани текущую маршрутизацию LLM, review-first стратегию и существующие данные. Не возобновляй намеренную полную паузу Kwork автоматически: отдели её от политики паузы по коннектам и документируй совместимость.

Ключевые требования:
1. Защити API и все Telegram routers/FSM/callbacks: user/chat авторизация, принадлежность pending карточке и версии. Ограничь публикацию внутренних портов и убери фиксированные credentials из compose.
2. Введи единый Alembic migration workflow. Подготовь read-only preflight существующей схемы и дублей. Добавь необходимые UNIQUE/CHECK/индексы без автоматического удаления конфликтующих данных. Проверь чистую установку и upgrade старой схемы на отдельной БД.
3. Durable inbound и outbox: checkpoint не опережает сохранение сообщения; уведомления и embeddings восстанавливаются после сбоя. Раздели получение, обработку и доставку.
4. Атомарные DB claims/leases для pipeline и отправки, общий send-attempt сервис для Telegram/worker/scripts. Не держи транзакцию во время сетевых вызовов. Фиксируй immutable snapshot отправляемой версии и связь job/proposal/thread.
5. Для внешней отправки различай confirmed_sent, known_failed и unknown_result. Timeout/commit failure после возможного успеха не разрешает слепой retry. Lease expiration тоже не доказывает отсутствие отправки. Сверяй с платформой, при неоднозначности запрашивай ручное разрешение. Не обещай exactly-once без поддержки idempotency площадкой.
6. Строго валидируй LLM ответы, scores и learning weights. Ошибка обработки не должна сохраняться как бизнес-отказ; некорректный JSON не должен получить проходной балл. Ограничь retries/timeouts/concurrency.
7. Точная идентичность заказа/клиента/thread вместо substring matching. Общий context service для API и inbox, история фактических отправок отдельно от draft, корректная инвалидация summary cache. Не объединяй неизвестных клиентов по NULL ID.
8. Идемпотентные outcomes/rewards, сначала outcome затем learning; learning получает реально отправленный текст и версию. Embedding provider независим от LLM; не используй hash-векторы как семантическую память. Qdrant — асинхронный и опциональный для генерации.
9. Исправь относительные scraper links/устойчивые IDs/optional fields. Явно обозначь stubs площадок. Подготовь lockfile, CI, production compose, readiness, backup/recovery runbook и актуальные README/.env.example.

Верификация:
- Unit tests без текущей даты и внешних credentials.
- Integration tests на отдельной PostgreSQL/Redis с fake LLM/Telegram/Kwork.
- Повтор callback, параллельные процессы, повтор beat, crash/restart, timeout-after-send, commit failure, сбой уведомления, миграция дублей, неоднозначный thread и повтор hired.
- Полный fake сценарий: заказ → оценка → proposal → approval → подтверждённая отправка → inbound → context → draft/edit → approval → reply → hired → однократный reward и memory.
- Запусти pytest, ruff check app tests scripts, pip check, проверки миграций и Docker config/build по необходимости.

Границы исполнения: разрешены локальные изменения и изолированные проверки. Не отправляй реальные Telegram/Kwork сообщения, не расходуй коннекты и не вызывай платные LLM для тестов. Не применяй миграции к действующей БД и не меняй production deployment. Подготовь всё до готового проверяемого результата; для конкретного внешнего действия получи отдельное разрешение. Не выводи .env, tokens/cookies и секреты в логи или отчёт. Не добавляй масштабную перепись архитектуры, новый frontend или новые площадки вместо исправления дефектов.

Веди docs/remediation-progress.md: что подтверждено, что изменено, этапы, результаты тестов, закрытые чеклисты, ограничения, оставшиеся задачи и точная команда продолжения. Продолжай разрешённые работы автономно. Если работу нужно продолжить в следующей сессии, оставь точное состояние и не называй незавершённый этап готовым.

В финале сообщи кратко: что исправлено, результаты проверок, какие критерии ещё не проверены, есть ли изменения схемы/конфига и что требуется перед реальным запуском. Дай ссылки на progress и обновлённые документы.
```

## Вариант для исполнения только одного этапа

Добавь к промпту:

```text
В этой задаче выполни только этап N из docs/remediation-plan.md и необходимые ему подготовительные изменения. Не переходи к следующим этапам. Если обязательная зависимость не выполнена, сначала реализуй минимальную часть зависимости и явно укажи её в progress. Критерий готовности — соответствующий раздел чеклиста с фактическими доказательствами. Не ограничивайся планом.
```

Для первого запуска рекомендуется этап 0, затем этап 1. Для длительной автономной работы используй основной промпт целиком.
